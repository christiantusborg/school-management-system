01

The four access states

Every controllable item carries one state per role. Actions (buttons) use only the two ends (Edit = allowed, Hidden/No-access = denied); fields, sections and tabs use all four.

E Edit
Full read + write. Can change the value / perform the action.
V View
Read-only. Sees the value but every control is disabled.
N No-access
Shown as present but locked (🔒), value masked; the server rejects reads and writes.
H Hidden
Not rendered at all — the field / section / tab does not exist for this role.
Enforcement, both ends
The server is the gate: writes require Edit, reads require View or higher, and field values are stripped from API responses below View. The UI mirrors it — Hidden isn't rendered, No-access shows a lock, View disables controls, Edit is live.
02

Status-based access

The student flow already has 15 ordered statuses, each with a Level and a NextActionRole (who must act next) — so this dimension has real structure to hang off. A second grid gives each role an access state per status:

  • See — a student whose current status the role can't see (Hidden) is filtered out of the list and drawer for that role.
  • Act — View lets the role open the student read-only; Edit lets them change data and perform the status transitions available at that step (approve, reject, defer, drop-out, submit/approve grades…).

04

Data model & enforcement

Storage — extend, don't replace

  • RolePermission gains an AccessLevel (Hidden / NoAccess / View / Edit) instead of a bare Allowed bool. Phase-1 grants migrate: Allowed=true → Edit, absent → Hidden.
  • New RoleStatusAccess (RoleName, StatusId, AccessLevel) — the status grid.
  • The item catalogue stays in code, now carrying a ResourceType (Tab / Section / Field / Action) that decides which of the four states are offered.
  • The audit log records level changes (old → new) for both grids, as in Phase 1.

Enforcement

  • Server — a resolver returns a role's level for a key: writes need Edit, reads need ≥ View. Field-level: responses omit fields below View; save handlers reject changes to View/No-access fields. Status: list queries filter to the role's visible statuses; transition endpoints check the status level.
  • Client — auth.access(key) returns the level; components render Hidden (nothing), No-access (lock), View (disabled), Edit (live). auth.can(key) from Phase 1 keeps working (true when level ≥ Edit).
  • Super Administrator bypasses everything, as today.
This is the big one
Field-level enforcement means touching every real admin surface (the ~140 items) on both the API and the UI, plus a status filter on student queries. It's the bulk of the work — planned as one release per your call, but it's genuinely large; the item counts above are the honest scope.
05

The editor

System Config → Roles & Permissions grows two views. Permissions: the catalogue grouped by surface into collapsible sections; each item row × six roles, each cell a compact E / V / N / H selector (Super locked on Edit). Statuses: a second grid of the 15 statuses × six roles. Saving either writes the level and appends to the same change-history the SuperAdmin already sees.

06

Decisions to confirm

  • No-access vs Hidden for actions. Buttons have no "read", so a denied action is either Hidden (gone) or No-access (shown, locked). Proposed default: Hidden for buttons, with No-access available where you'd rather show "you can't do this".
  • Aggregate anonymity gate stays. The 3-response minimum for cohort/questionnaire aggregates is a privacy rule, not a permission — it stays regardless of the matrix.
  • Status "See" vs partner scoping. Sales' partner-scoping stays as-is; status visibility is an additional filter layered on top, not a replacement.
  • Grade values. Should "View" on Grades show the numbers read-only, or should grades be a No-access (masked) option for some roles? Proposed: View shows them; you can set No-access per role if needed.
