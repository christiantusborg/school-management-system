01

How access works today

Admin "levels" are not a database column or an enum — they are ASP.NET Identity roles. Every admin holds the base Admin role plus exactly one level role: SuperAdministrator, Administrator, Manager, Editor, Viewer, or Sales.

There is no central rulebook. What each level can do is enforced in three disconnected places:

  • One coarse path middleware that only knows Admin / Partner / Student — not the levels.
  • Roughly 30 hand-written checks in the API (IsInRole("SuperAdministrator") and the like), each guarding one action.
  • Roughly 20 matching checks in the UI that show or hide buttons and tabs.

That scattered set is the current access matrix — it's just written in code instead of a table. This spec lifts it into one editable, server-enforced matrix, reproduced exactly (§4) so nothing changes on the day it ships.

Kept as-is: Sales data scoping
Sales users see only their own assigned partners' students, leads and mail. That's row-level filtering, not a simple on/off — so it stays exactly as it is today. The matrix governs actions (can / can't), not which rows a user sees.

03

How it's enforced

Server (the real gate)

A single helper — require("students.delete") — replaces each of the ~30 hand-written role checks. It returns 403 when the caller's role lacks the permission (Super Administrator always passes). The existing coarse path middleware stays as the first line (is this an Admin at all?); the fine matrix decides which admin action is allowed.

UI (what you see)

Login (/v1/me) returns the user's effective permission keys. The frontend gains auth.can("students.delete"), replacing the ~20 adminLevel === … branches, so buttons and tabs appear only when the action is permitted. This is convenience, not security — the server is the gate.

One source of truth
Today the level list is duplicated in three files. After this, the permission catalogue and each role's grants are defined once; the UI and API both read the same resolved set.

05

The editor & the audit trail

System Config → Roles & Permissions (Super Administrator only) shows this exact grid with checkboxes: rows are permissions grouped by area, columns are the six roles. The Super Administrator column is locked on — it always has everything. Saving a change writes the grant and appends to the audit log.

A History panel on the same tab lists every change: who made it, when, which role and permission, and the before → after value. Nothing is deleted; the trail is append-only.

To confirm during the build

  • Two ambiguous gates (marked verify): students.regenerate_letters and letters.email_edit — the UI and API appear to disagree on Manager/Editor. The API (the real gate) is authoritative; I'll read the exact code and seed to match.
  • Deliberate least-privilege rules to preserve: students.remove_programme was intentionally tightened to SuperAdmin ("verified live: an Administrator gets 403"). The seed keeps it that way.
  • Sales scoping stays hard-coded — the matrix does not (yet) make "sees all vs sees own" configurable.
  • Migration surface: ~30 API checks + ~20 UI checks + 3 duplicated level lists to converge on one source.
Risk to manage
This touches the security-critical path across ~50 sites. Each replacement keeps the same effective rule; the plan is to migrate area by area and confirm the seed reproduces today's behaviour before the editor is opened up.
